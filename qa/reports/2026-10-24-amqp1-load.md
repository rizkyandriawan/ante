# AMQP 1.0 load test — 2026-10-24

Baseline end-to-end load through the AMQP 1.0 acceptor after adding credit-aware claims,
link-detach detection, bounded SASL/Open handshakes, explicit binary-ID
rejection, and abort-without-flush cancellation for ambiguous transfers.

These measurements predate the ordered transport-completion marker. See
[transfer regression verification](2026-10-24-amqp1-transfer-regressions.md)
for the subsequent correctness checks and post-change load run.

Workload: 20,000 jobs of 1 KiB, four producer connections and four consumer
connections over loopback TCP, each with its own session and link. The client
waits for `Accepted` on every publish, and every received payload carries a
unique job index. Throughput includes one durable SQLite commit per publish, one
settlement per delivery, and the final queue-drained barrier.

Environment: Linux x86_64, 20 logical CPUs, ext4 on NVMe, release build,
`fe2o3-amqp` 0.18.4 with the local `Sender::credit()` and abort controls,
plaintext profile (no TLS/SASL).

| Run | Jobs | Wall | Throughput | Publish p50 | Publish p99 | Peak RSS | DB | Duplicates |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 20,000 | 37.05 s | 539.9 /s | 3.77 ms | 10.08 ms | 28.2 MiB | 17.52 MiB | 0 |
| 2 | 20,000 | 38.17 s | 524.0 /s | 3.89 ms | 21.42 ms | 28.3 MiB | 17.28 MiB | 0 |
| 3 | 20,000 | 36.42 s | 549.1 /s | 3.87 ms | 21.38 ms | 27.8 MiB | 17.18 MiB | 0 |

Median: 37.05 s, 539.9 jobs/s, publish p50 3.87 ms, publish p99 21.38 ms,
28.2 MiB peak RSS, 17.28 MiB database. Every run acknowledged all 20,000 unique
jobs and ended with an empty queue.

Headroom run: 50,000 jobs completed in 127.26 s (392.9 jobs/s) with zero
duplicates and a drained queue; peak RSS was 48.5 MiB and the database was
36.73 MiB.

Cancellation semantics: if a transfer is still buffered when its claim expires
or the sender stops, Ante shuts down the connection socket with zero linger and
aborts the protocol connection, so queued frames are not flushed. All links on
that connection reconnect, and unresolved deliveries are requeued. Deliveries
whose `Accepted` disposition was already recorded stay acked. The separate
`amqp1_accepted_outcome_is_durable_before_close` test checks that the broker
persisted the ACK before close, and `amqp1_accept_then_immediate_close_does_not_stall`
covers the accept-then-close race; this load run measures the steady-state path.

The `batch` and `window` flags are accepted by the shared benchmark CLI but are
unused in `amqp1` mode: every publish is one durable commit and one confirmed
transfer. `consume_batch_us` measures only the disposition call, so its
sub-microsecond values are not reported here.

Limits: local loopback, one queue, four producers/four consumers, no TLS/SASL,
no process crash or power loss. Throughput is per-message durable publish plus
settlement, so it is not comparable to the batched native benchmark. This is a
regression/load check, not a release capacity claim.

Reproduce:

```bash
cd bench
cargo build --release -p e2e-bench
for run in 1 2 3; do
  ./target/release/e2e-bench amqp1 --total=20000 --batch=100 --payload=1024 --rep=$run --mode=both
done
./target/release/e2e-bench amqp1 --total=50000 --batch=100 --payload=1024 --rep=1 --mode=both
```
